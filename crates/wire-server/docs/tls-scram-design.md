# ADR: TLS・SCRAM 実運用設計・導入方式確定（WIRE-9）

- ステータス: Proposed（決定点はオーナー確定待ち。確定後、別コミットで Accepted に更新する）
- 対応: TASK-72（MS-3 / phase:3・wire プロトコル層・WIRE-9）
- 関連: TASK-70（未実装・後続タスク）

## 背景

wire プロトコル層は PostgreSQL wire プロトコル v3 互換の自作実装であり、
psql・psycopg・node pg が無改造で接続可能なことを PoC-8 で実測済みである
（README.md「実装方針（要点）」）。今後、非 loopback な環境へ配置する運用を
見据えると、通信路の暗号化（TLS）と認証方式（SCRAM）の扱いを事前に整理して
おく必要がある。本タスクはコード実装ではなく、導入方式を判断するための設計
ドキュメントを作成するタスクである（詳細な決定理由・現状の認証方式は private
spec 側の該当タスクを参照する。本ドキュメントは公開範囲に収まる設計提案のみを
記述する）。

現状の `crates/wire-server` は TASK-66 時点の stub（`src/main.rs` のみ）であり、
TCP 待ち受け・SSLRequest ハンドシェイク・認証フローは未実装である。本タスクは
その実装に着手する前段の設計整理であり、ランタイム挙動を変更しない。

## 設計方針（提案）

### TLS（通信路暗号化）

- 非 loopback 運用では、クライアント〜wire-server 間の通信路を平文のまま公開しない
  ことを既定方針とする（fail-closed）。
- pg wire v3 は接続開始時に `SSLRequest` を送出し、サーバーが `S`（TLS へ移行）
  または `N`（TLS 非対応）で応答するネゴシエーションを持つ。自作 wire 実装では、
  接続受理直後・スタートアップメッセージ解析より前にこのネゴシエーションを処理する
  組み込みポイントを設ける想定とする。
- 証明書管理方式の選択肢:
  - **運用者提供の cert/key ファイル指定（推奨案）**: 起動時オプション等で
    証明書ファイル・秘密鍵ファイルのパスを指定させる方式。実装がシンプルで、
    既存の証明書運用（社内 CA・自己署名証明書等）と独立に扱える。
  - 自動生成・ACME 連携等: 本タスクではスコープ外とする。運用が複雑化するため、
    必要になった時点で別タスクとして再検討する。

### TLS ライブラリ候補

- 依存最小方針（[dependency-policy](../../../.claude/rules/dependency-policy.md)）
  との整合を最優先とする。TLS はプロトコル実装が複雑であり自作コストが高いため、
  外部クレートへの依存が現実的な候補となる（wire プロトコル本体の自作方針とは
  別軸の判断）。
- 候補比較の観点（採用判断時に dependency-policy の承認情報 4 項目として提示する）:
  1. クレート名・バージョン（`=x.y.z` 完全固定）・目的
  2. ライセンス（MIT / Apache-2.0 互換であること）
  3. メンテナンス状況（最終リリース日・リポジトリの活動状況）
  4. 推移的依存の概要（大量の間接依存を引き込まないか）
- 純 Rust 実装の TLS ライブラリ（例: rustls 系）は OpenSSL 系バインディングと比べて
  ビルド依存・推移的依存が少ない傾向があり、比較の出発点として扱う。
- **本タスクでは依存を追加しない。** ライブラリ選定・バージョン固定はユーザー承認を
  経た後続タスクで行う。

### SCRAM（認証方式）

- SCRAM は通信路暗号化（TLS）とは別軸の要件であり、独立に採否を判断する。
- SCRAM-SHA-256（RFC 5802 の SCRAM 機構、RFC 7677 の SHA-256 バリアント）は
  PostgreSQL wire プロトコルで標準的に使われるチャレンジ・レスポンス型認証であり、
  パスワードそのものをネットワーク上に送出しない・タイミング攻撃への耐性を持つ
  実装が可能という利点がある。
- 単純なパスワード方式（平文送出）との一般的な比較:
  - 平文パスワード方式: 実装が単純だが、TLS 非構成の経路では露出する。
  - SCRAM-SHA-256: サーバー側にソルト付きハッシュを保持し、チャレンジ・レスポンスで
    検証する。実装コスト（メッセージフォーマット・状態機械・ハッシュ計算）は高い。
- 採否の確定タイミング: 本タスクでは採用可否そのものは決定せず、判断材料の整理に
  留める（確定時期・現行の認証方式は private spec 側を参照する）。

### 既存設計との整合

- WIRE-7（TASK-70。未実装・後続タスク）は本ドキュメントと関連する wire プロトコル層
  のタスクであり、TLS 構成の有無との関係は WIRE-7 実装時に確定する（詳細は private
  spec 側を参照する）。

## 決定点一覧（オーナー確定待ち）

| 決定点 | 推奨案 | 判断材料 |
| ------ | ------ | -------- |
| 証明書管理方式 | 運用者提供の cert/key ファイル指定 | 実装の単純さ／既存証明書運用との独立性／自動発行（ACME 等）は運用複雑化のためスコープ外 |
| SCRAM 採否 | 採用の方向で検討（確定時期は private spec 側を参照） | 平文パスワード方式は TLS 非構成時に露出／SCRAM-SHA-256 は実装コストが高いが送出情報を最小化できる |
| TLS ライブラリ選定・依存承認 | 純 Rust 実装系ライブラリを比較の出発点とする | dependency-policy の 4 項目（バージョン固定・ライセンス・メンテ状況・推移的依存）で比較し、ユーザー承認を得てから確定 |

## 影響

- TLS ハンドシェイク・証明書ロードの実装: 本決定確定後の後続実装タスクで対応
  （TASK-72 より後の wire プロトコル層タスク。具体的なタスク ID は spec 側で確定）
- SCRAM 認証フローの実装: 採否確定後の該当タスクで対応
- WIRE-7（TASK-70）: 本ドキュメントの「既存設計との整合」節の前提を実装時に反映する

## スコープ外

- TLS・SCRAM の実装コード（SSLRequest ハンドシェイク・証明書ロード・SCRAM
  チャレンジ・レスポンス）
- TLS ライブラリの依存追加（Cargo.toml への追加はユーザー承認後の後続タスク）
- `docs/spec` 側ドキュメントへの本決定の反映（spec リポジトリ側の作業であり、本
  リポジトリから submodule を変更しない）
