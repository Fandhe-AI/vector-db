# ADR: 並行書き込み検証と永続化層の移行判断

- ステータス: Proposed（本 PR のマージ後、別コミットで Accepted に更新する）
- 対応: TASK-144（MS-1 / phase:1・基盤・工程管理・Conditional Go 条件6）
- 前提: TASK-140（`redb` 永続化層、Issue #16 / PR #118 でマージ済み）
- 関連: `docs/spec/06-roadmap.md`（MS-1）

## 背景

`redb` は書き込みトランザクションが排他ロックで直列化される。複数クライアントが
同時に書き込む実運用形態で待機時間・スループットがどの程度劣化するかは未実測であり、
`redb` 継続か代替（`sled`・自作 MVCC 等）への移行かの判断材料が無かった。本 ADR は
その実測結果と移行判断（Proposed）を記録する。

## 検証設計

### 並行モデル

本アーキテクチャは単一サーバプロセス（wire-server）が複数クライアント接続を受ける
構成のため、「複数クライアント同時書き込み」を単一プロセス内の複数スレッドが
`Arc<Storage>` を共有して同時に書き込む形でモデル化した。`redb` はプロセス内共有が
前提のバックエンドであるため、この対応は妥当と判断する。`Storage` は `Send + Sync`
であり `Arc` 共有に追加の変更は不要だった（`crates/engine/src/storage.rs` は本検証で
変更していない）。

### 正しさの回帰テスト（CI 常時実行）

`crates/engine/tests/concurrent_write.rs` に、8 スレッドが `Arc<Storage>` を共有し
重複しない id 範囲へ `put` / `put_batch` する 2 本のテストを追加した。全スレッド
join 後に `scan_page` のページングで全行を読み切り、欠損・破損・二重化がないことを
検証する（`scan()` は行サイズ・件数次第で総バイト量上限を超え得るため使わない）。
時間依存のアサーションは含めない。

### 実測ハーネス（手動実行専用）

`crates/engine/examples/concurrent_write_bench.rs`（`cargo test` の対象外。
`cargo run -p engine --release --example concurrent_write_bench` で実行）。
スレッド数 {1, 2, 4, 8} × 書き込み方式 {`put` 単発, `put_batch`（20 件/バッチ）}
の全 8 設定で、1 設定あたり 800 行を書き込み、操作（`put` 1 回 or `put_batch` 1 回）
ごとの所要時間の p50/p95/max と全体スループット（rows/sec）を計測する。
行データは 768 次元 f32 埋め込み＋64 バイトメタデータ（現実的なベクトル行サイズを想定）。
行数・スレッド数・行サイズはすべて定数で上限固定した。

## 実測環境

| 項目 | 値 |
| ---- | -- |
| CPU | Apple M4 Max（16 コア） |
| OS | macOS 26.6.2（Darwin 25.6.0 / arm64） |
| ストレージ | 開発機ローカル SSD（`std::env::temp_dir()` 配下） |
| ビルド | `cargo run --release` |

**注意（測定条件の限界）**: 本測定は開発機上で、他の Issue 実装用 worktree が
同時稼働している共有環境で実施した。CPU・I/O 競合により、専有環境での再実測より
遅い値・ばらつきの大きい値が出ている可能性がある（実際、初回実測では 1 スレッド
`put_batch` のみ約 796 rows/sec と他の全設定から外れた値が出たが、直後の再実行
2 回では 3000〜3900 rows/sec の範囲に収まり、初回値が瞬間的な競合によるスプリアス
値だったことを確認した。下表は再実行時点の値を採用する）。専有環境での再実測は
「スコープ外」節を参照。

| 1 | put(single) | 800 | 4.247ms | 5.232ms | 9.857ms | 3.525s | 226.9 |
| 2 | put(single) | 800 | 4.571ms | 16.073ms | 396.035ms | 3.615s | 221.3 |
| 4 | put(single) | 800 | 4.431ms | 32.562ms | 2.200s | 4.383s | 182.5 |
| 8 | put(single) | 800 | 4.419ms | 45.497ms | 1.889s | 3.663s | 218.4 |
| 1 | put_batch | 40 | 5.082ms | 9.804ms | 10.883ms | 210.675ms | 3797.3 |
| 2 | put_batch | 40 | 9.812ms | 21.211ms | 51.990ms | 219.540ms | 3644.0 |
| 4 | put_batch | 40 | 20.003ms | 41.193ms | 71.627ms | 215.648ms | 3709.7 |
| 8 | put_batch | 40 | 39.036ms | 106.550ms | 117.243ms | 205.890ms | 3885.6 |

（`op_count` は「操作回数」であり、`put_batch` の 1 op は 20 行を含む。
`total` は全スレッド join までの経過時間、`rows/sec` は `ROWS_PER_CONFIG / total`。
共有環境での測定ノイズにより数値は実行ごとに数百 rows/sec 程度変動し得る。）

### 観察

- **単発 `put` はスレッド数によらずスループットがほぼ一定**（約 183〜227 rows/sec）。
  直列化された書き込みトランザクションのコミットコスト（`redb` の I/O 同期含む）が
  支配的で、並行度を上げても総スループットは改善しない。これは `redb` の直列化契約
  （`begin_write` の排他ロック）から予測される挙動そのものであり、実測もそれと整合
  する。一方 p95/max はスレッド数増加とともに悪化する傾向がある（4〜8 スレッドで
  max が秒オーダーに達する）。これは直列化された書き込みキューで後続スレッドが
  待たされるためである。
- **`put_batch` はスレッド数によらずスループットがほぼ一定**（約 3600〜3900 rows/sec、
  単発 `put` の約 16〜21 倍）。1 トランザクションで複数行をまとめてコミットする
  ことで、コミットあたりの I/O 同期コストを行数で償却できる。単発 `put` と同様に
  「直列化された 1 本のキューを複数スレッドが共有している」というモデルと整合する
  結果であり、スレッド数を増やしても頭打ちのスループットが変わらない点はむしろ
  直列化の理解を裏付ける。
- 総じて、書き込みトランザクションの直列化自体はレイテンシの尾（p95/max）を
  悪化させるが、総スループットは `put_batch` の活用で単発 `put` の 1 桁台後半〜
  20 倍程度まで引き上げられる。

## 移行判断（Proposed）

**`redb` を継続する。** 根拠:

1. 正しさは全設定で担保されている（回帰テストで確認・欠損なし）。
2. `put_batch` によりスループット劣化を実用上許容できる水準まで緩和できる
   （呼び出し側でバッチ化する余地が大きい）。
3. `sled`・自作 MVCC への移行は新規依存の追加または大規模な自作実装コストを伴い、
   dependency-policy.md のユーザー承認プロセスが必要な大きな決定である。本測定の
   結果は移行を必須とするほどの劣化を示していない。
4. 単発 `put` の p95/max 悪化は、wire-server 側で書き込みをバッチ化する設計
   （TASK-144 より後続のタスク）で緩和できる可能性が高く、永続化層自体の
   置き換えより低コストな対応で足りると考えられる。

この判断は Proposed とし、PR レビューでの承認をもって Accepted とする。

## スコープ外

- `sled` / 自作 MVCC への実移行（本判断が将来変わる場合も、依存追加・設計変更は
  別 Issue・ユーザー承認事項とする）
- 専有環境・実 wire 接続経由での再実測（Conditional Go 条件7 系タスクや後続で扱う）
- wire-server 側での書き込みバッチ化設計（後続タスクの検討事項として記録するのみ）
- `docs/spec` submodule の変更（spec リポ側の作業。本リポからは触らない）
