# Ed25519 署名生成（RFC 8032）と CertificateVerify 実装記録

- ステータス: Accepted（実装記録）
- 対応: TASK-228（WIRE-9・HTTP-10 ポインタ）・Issue #961・親 Issue #941

## 背景

親 Issue #941（TLS 1.3 サーバー側自作実装）はサーバー証明書の鍵種別を
Ed25519 に限定する方針を取る（`signature_algorithms` は 0x0807 のみ
受理。判定は `client_hello::negotiate` が担う）。ハンドシェイクでは
サーバーが `CertificateVerify`（RFC 8446 §4.4.3）に Ed25519 署名を
載せる必要があり、本 Issue はその署名生成・検証（RFC 8032 §5.1）と
`CertificateVerify` の署名対象組み立て・生成・検証を実装する
（`crates/wire-server/src/tls/ed25519.rs`・`certificate_verify.rs`）。

前提として `field25519.rs`（Issue #955。GF(2^255-19) の定数時間算術。
X25519 と共有）・`sha512.rs`（Issue #960）・`pkcs8::Ed25519Seed`
（Issue #962）・`x509::ServerCertificateChain::from_der_chain`
（Issue #963）・`handshake::CertificateVerify`（Issue #953）・
`client_hello::SIG_ED25519`（Issue #954）・`transcript::Transcript`
（Issue #964）がすでに実装済み。

alert の実送出・ハンドシェイク状態機械への組み込み（#965）、起動時の
鍵読み込み → 公開鍵導出 → x509 照合の CLI 結線（#967）、クライアント
証明書とクライアント側 `CertificateVerify`（親 #941 の対象外）はいずれも
対象外のまま。

## 表現・定数時間性の根拠

- 曲線点は拡張座標 `EdwardsPoint { X, Y, Z, T }`（`x=X/Z`・`y=Y/Z`・
  `xy=T/Z`）で保持する非公開型。加算式は RFC 8032 §5.1.4 の統一加算式
  （twisted Edwards `a=-1` に対して完全（complete）であり、単位元・
  自己加算を含むあらゆる入力の組で例外分岐が不要）、doubling は専用の
  add-2008-hwcd 系の式（curve25519 系実装で広く使われる公知の手法）。
  いずれも実装時に affine 参照実装（独立な多倍長整数計算）と数値的に
  照合済み。
- スカラー乗算（`scalar_mul`）は 256 回固定の double-and-add-always。
  ビットの抽出は公開のループカウンタのみを添字に使い（`k[t >> 3]`）、
  分岐・テーブル参照は行わない（X25519 の ladder と同じ設計方針）。
  各ラウンドの候補点を選ぶ `EdwardsPoint::select` は `Fe::select`
  （`mask = 0 - choice` による XOR マスク）を 4 座標へ適用するのみ。
- mod L（群位数 `L = 2^252 +
  27742317777372353535851937790883648493`）のスカラー演算
  （`ed25519::scalar` サブモジュール）:
  - `reduce512`: SHA-512 出力（512 ビット）のビット単位 Horner 法
    （上位ビットから `acc = 2*acc + bit`・都度 `acc >= L` ならボロー
    マスクによる条件付き減算）。512 回固定ループで秘密値に依存する
    分岐・添字を持たない。
  - `mul_add`（`S = r + k*a mod L`）: 当初は 4×4 limb の教科書的乗算を
    `u128` へ蓄積する設計だったが、部分積の列総和が `u128`
    （2^128 未満）を超えてオーバーフローする実装バグを RFC 8032 §7.1
    TEST SHA(abc)（メッセージが長く nonce `r` が大きくなるケース）で
    検出した。代わりに、`a`（クランプ済みスカラー。クランプにより
    `bit254` が常に立ち `a >= 2^254 > L` となるため `< L` の前提を
    満たさない）の各ビットを最上位から読みながら
    `acc = 2*acc mod L`・ビットが立っていれば `acc += k mod L`
    （`k`・`r` はいずれも `reduce512` の出力で `< L`）を繰り返す
    二進乗算（Horner 法）へ置き換えた。`acc` はループ全体を通して
    常に `< L` に保たれるため、`add_mod_l`（`x + y < 2L` の前提下で
    1 回の条件付き減算のみで `mod L` に収まる）の前提を満たし、
    加算ごとの中間値は最大でも 257 ビット程度にとどまる。`a` の値
    そのもの（秘密値）に依存する分岐は `select_limbs`
    （`Fe::select` と同じマスク方式）に置き換え、256 回固定ループで
    秘密添字も持たない。
  - `is_canonical`（`S < L`）は検証専用の公開値判定であり、分岐が
    あってもよい。
- 鍵展開（`SigningKey::from_seed_bytes`）は RFC 8032 §5.1.5 のクランプ
  （`a[0] &= 248`・`a[31] &= 63`・`a[31] |= 64`）を行い、seed・展開後の
  SHA-512 出力（64 バイト）を使用後に `hkdf::zeroize` する。

## 点復元・非正準入力

- `EdwardsPoint::decompress`（RFC 8032 §5.1.3）は**公開値専用**
  （検証対象の署名 `R`・公開鍵 `A`）であり、分岐は入力の形状にのみ
  依存する定数時間性でよい。
  - `y` の正準性検査: `Fe::from_bytes` は bit 255 を無条件でマスクする
    ため、符号ビットを取り出した後のバイト列と `y.to_bytes()` を比較し、
    `p` 以上の非正準表現を拒否する。
  - 平方根候補は `x = u * v^3 * (u*v^7)^((p-5)/8)` で直接計算する
    （逆元計算を経由しない標準的な手法）。`(p-5)/8 = 2^252-3` の指数は
    新設の `Fe::pow_p58` が担う。
  - `v*x^2` が `u` と一致すればそのまま、`-u` と一致すれば
    `x *= sqrt(-1)`、どちらでもなければ「平方根が存在しない」として
    拒否する。
  - `x == 0` かつ符号ビットが 1 の表現（非正準）を拒否する。
  - 符号ビットと `x` の偶奇が異なれば `x` を反転する。
- `Fe::pow_p58` は `Fe::invert`（`self^(p-2)`）と共通の固定長加算連鎖
  `pow_2_250_minus_1_and_11`（`self^(2^250-1)` と `self^11` を返す）を
  共有する。`invert` は続きに 5 回の平方＋1 回の乗算、`pow_p58`
  （`self^(2^252-3)`）は続きに 2 回の平方＋1 回の乗算を追加するだけで
  導出できる関係（`2^252-3 = (2^250-1)*4+1`・`p-2 = (2^250-1)*32+11`）を
  使う。`invert` の出力はこの再構成の前後でビット同一（既存の X25519
  RFC 7748 テストで確認済み）。
- 自己整合性の単体テスト: フェルマーの小定理 `x^p ≡ x`（`x != 0`）から
  導かれる `pow_p58(x)^8 * x^5 == x` を確認する。

## API・alert 写像

- `SigningKey::from_seed(&Ed25519Seed)` / `from_seed_bytes([u8;32])`:
  鍵展開の入口。前者が PKCS#8（`pkcs8::Ed25519Seed`）からの正規経路
  （#967 が結線）、後者は結合テスト・RFC 8032 §7.1 の公開ベクタ検証用。
  `Clone`/`Copy` は導出せず、`Debug` は内容を伏せ、`Drop` で
  `scalar`・`prefix` を best-effort ゼロ化する。seed 自体は展開後は
  保持しない（ゼロ化すべき秘密バイト量を最小にする設計判断）。
- `SigningKey::public_key() -> [u8; 32]`:
  `x509::ServerCertificateChain::from_der_chain` の
  `expected_leaf_public_key` へ渡す値（起動経路の接続は #967）。
- `SigningKey::sign(&self, message: &[u8]) -> [u8; 64]`: RFC 8032
  §5.1.6 の決定的署名。
- `ed25519::verify(public_key, message, signature) -> Result<(), Ed25519Error>`:
  自己整合性テスト用（サーバーはクライアント証明書を扱わないため
  production 経路での呼び出し元は無い）。`[S]B == R + [k]A`
  （cofactor を掛けない判定式。RFC 8032 が許容し §7.1 のベクタも通る）
  を、圧縮 → デコードの往復を経ずに拡張座標の交差乗算
  （`X1*Z2 == X2*Z1 && Y1*Z2 == Y2*Z1`）で判定する（`compress` が伴う
  逆元計算を避ける）。
- `Ed25519Error::alert_description`: 署名長不正は `decode_error`、
  非正準スカラー・鍵/点の不正・検証失敗はいずれも `decrypt_error`
  （RFC 8446 §4.4.3）へ写像する。
- `certificate_verify::server_signed_content(transcript_hash: &[u8; 32]) -> [u8; 130]`:
  0x20 を 64 個 ‖ `"TLS 1.3, server CertificateVerify"` ‖ 0x00 ‖ hash。
  `transcript_hash` は呼び出し元（#965）が
  `transcript::Transcript::hash_through_certificate()` の戻り値を
  そのまま渡す契約（`Transcript` 自体には依存しない。`finished.rs` と
  同じ設計判断）。
- `certificate_verify::build_server_certificate_verify` /
  `verify_server_certificate_verify`: 曲線演算より前に
  `algorithm != SIG_ED25519`（`illegal_parameter`）・署名長不正
  （`decode_error`）を拒否してから `ed25519::verify` へ委譲する。
  クライアント側のコンテキスト文字列（`"TLS 1.3, client
  CertificateVerify"`）・クライアント証明書は対象外。

## 検証

RFC 8032 §7.1 の公開テストベクタ（TEST 1・TEST 2・TEST 3・
TEST SHA(abc)）は、記憶からの転記ではなく独立な Python 参照実装
（RFC 8032 §5.1 の公開アルゴリズムをそのまま実装したもの。本リポの
Rust 実装とは完全に別系統）で事前に再現・照合したうえで固定した
（単体テスト・結合テストの双方）。曲線パラメータ `d`・`2d`・
`sqrt(-1)`・基点座標・群位数 `L` も同じ方法で導出し、代数的な定義式
（`d*121666+121665 ≡ 0`・`sqrt(-1)^2 ≡ -1` 等）を満たすことを単体
テストで固定した（転記ミスの検出）。

- 単体テスト（`tls::field25519::tests`）: `neg`・`select`・`equals`・
  `zeroize`・曲線定数の代数的関係・`pow_p58` の自己整合性・
  `pow_p58(0) == 0`。
- 単体テスト（`tls::ed25519::tests`）: RFC 8032 §7.1 の 4 ベクタ
  （公開鍵・署名の完全一致・検証成功）、決定性、R/S/メッセージの
  ビット反転・別公開鍵・長さ 0/63/65・`S >= L`・R の非正準表現・
  平方根が存在しない公開鍵・`x=0` かつ符号ビット 1 の公開鍵の拒否、
  `Debug` の秘匿、`Drop`/`wipe` によるゼロ化、基点の圧縮往復、単位元の
  圧縮値、`[L]B == 単位元`。
- 単体テスト（`tls::ed25519::scalar::tests`）: `reduce512` の境界
  （0・L・L-1・2L・2^512-1）、`mul_add` の小さな値・`(L-1)^2 mod L == 1`、
  `is_canonical` の境界。
- 単体テスト（`tls::certificate_verify::tests`）: 署名対象バイト列の
  レイアウト固定、生成・検証の往復、`ed25519::sign` との一致、
  hash 改変・algorithm 不一致・署名長不正の拒否、alert 写像、
  `Display` に秘密バイトが含まれないこと。
- 結合テスト（`tests/tls_ed25519_rfc8032.rs`）: 単体テストと同じ
  RFC 8032 ベクタ・負のテストを公開 API 経由で再固定するとともに、
  RFC 8410 §10.3 v1 の PEM（`tests/tls_pem_pkcs8.rs` の
  `ED25519_V1_SEED_HEX` と同一値）を `pkcs8::decode_ed25519_private_key_pem`
  で読み、`SigningKey::from_seed` で導出した公開鍵が RFC 8410 §10.1 の
  公開ベクタ（`tests/tls_x509.rs` の `RFC8410_10_1_ED25519_PUBLIC_KEY`
  と同一値）と一致することを確認した（#967 が結線する起動経路――
  鍵読み込み → 公開鍵導出 → x509 照合――の初めての実証）。
  `CertificateVerify::parse`/`encode_into`（`handshake.rs`。Issue #953）
  との往復が本 Issue の生成物に対しても成立することもあわせて固定した。

## 残余リスク・申し送り（#971 監査への申し送り）

- ゼロ化は `unsafe`（`write_volatile` 等）を使わない best-effort であり、
  最適化による消去省略が起きない保証はない（`hkdf`・`sha512`・
  `pkcs8::Ed25519Seed` と同じ限界）。`scalar_mul` のスクラッチ点
  （各ラウンドの候補点を上書きし続ける専用変数）はループ終了後に
  ゼロ化するが、あくまで多層防御であり、最終的な戻り値（公開鍵・R 点。
  いずれも公開値）自体はゼロ化しない。
- `u128` を用いた演算がターゲット（x86_64・aarch64）で定数時間である
  ことを X25519 と同じ前提として置く。
- 決定的署名（RFC 8032）のため乱数品質には依存しない（nonce 再利用の
  構造的リスクが無い）。
- `EdwardsPoint::decompress`・署名検証・`is_canonical` は公開値
  （このサーバーの経路では自分の公開鍵・検証対象の署名に限られる）
  にのみ実行されるため分岐を許容しているが、クライアント証明書
  経路が将来追加された場合はこの前提が変わりうる（現時点では親 #941
  の対象外）。
