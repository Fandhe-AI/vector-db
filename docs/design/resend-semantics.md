# ADR: 同一パスファイル再送セマンティクス

- ステータス: Proposed（本 PR のマージ後、別コミットで Accepted に更新する）
- 対応: TASK-123（MS-1 / phase:1・基盤・工程管理）
- 反映先（実装・テスト）: TASK-120（INDEX-1/2）・TASK-93（RECOVER-2）
- 関連: TASK-92・TASK-80

## 背景

取り込み時に同一（テナント, テーブル, パス）のファイルが再送された場合、既存パス
由来のレコード（チャンク）をどう扱うか（置換するか・追加するか、重複排除が必要か）
を本実装がどう定めるかを規定する。TASK-120・TASK-93 の実装はこの決定に従う。

## 決定事項（推奨案: 置換セマンティクス）

同一（テナント, テーブル, パス）のファイル再送は「更新」とみなし、**既存パス由来の
レコードを削除して新レコードを挿入する置換**として扱う。削除と挿入は**単一トランザ
クションで原子的**に行う。

### 根拠

- 追加（append）方式では旧チャンクが検索結果に残り続け、本リポジトリの設計思想
  （「正解を含むデータ群を広く返す」）に反してノイズを増やす
- 置換方式であればパス単位の重複排除が自然に達成され、追加の重複排除機構を必要と
  しない

## 冪等性との整合

再送の冪等性キーによる no-op 判定（重複適用しない）は、既存の冪等性機構
（TASK-92・TASK-80）に従う。

## 重複排除の要否

パス単位の置換により重複排除は達成されるため、コンテンツハッシュによる no-op 最適化
（同一内容の再送を書き込みなしで終える最適化）は本決定のスコープ外とし、将来の最適
化課題とする。

## 失敗時の挙動（fail-closed）

置換トランザクションが部分的に失敗した場合は全体を abort し、旧レコードを維持する。
中途状態（削除済みだが未挿入等）を外部に可視化しない。

## セキュリティ前提

- パスはテナント内スコープのキーであり、削除対象の特定は必ずテナント境界内に閉じる。
  クロステナントでの削除が発生しうる経路を作らない
- パスは untrusted 入力として扱い、バイト列としての完全一致比較・長さ上限検証を前提
  とする。正規化による差異（大小文字・Unicode 正規化形式・末尾スラッシュ等）でのエイ
  リアス重複や、パストラバーサルとしての解釈は行わない

## 代替案の比較

| 案 | 内容 | 却下理由 |
| ---- | ---- | ---- |
| A. 追加（append） | 再送のたびに新規レコードを追加し、旧レコードは残す | 旧チャンクが検索結果を汚染し設計思想に反する。パス単位の重複排除も別途必要になる |
| B. コンテンツハッシュ突合による差分更新 | ファイル内容のハッシュを比較し、変化があった場合のみ置換する | 実装コストに対し本タスクの基盤決定としては過剰。将来の最適化として切り出す（本 ADR のスコープ外） |
| C（採用）. 置換（delete + insert の原子的処理） | 既存パス由来レコードを削除し新レコードを挿入する | 設計思想との整合性が高く、実装複雑度も追加方式より低い |

## 影響

- TASK-120（INDEX-1/2）: 取り込み処理で本決定に基づく削除+挿入の原子的処理を実装する
- TASK-93（RECOVER-2）: リカバリ処理で本決定と整合する状態復元を行う
- 上記 2 タスク側で本決定に対応するテストを追加する（本タスクは基盤・工程管理タスク
  であり、対応ビヘイビア ID なしのため本 PR ではテスト追加を行わない）

## スコープ外

- 置換セマンティクスの実装・テスト追加（TASK-120・TASK-93 側で対応）
- コンテンツハッシュによる no-op 最適化（代替案 B、将来課題）
- `docs/spec` 側への本決定の反映は spec リポジトリ側の作業であり、本リポジトリから
  は submodule を変更しない
