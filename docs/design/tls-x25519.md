# X25519 鍵交換（RFC 7748・定数時間）実装記録

- ステータス: Accepted（実装記録）
- 対応: TASK-228（WIRE-9・HTTP-10 ポインタ）・Issue #955・親 Issue #941

## 背景

親 Issue #941（TLS 1.3 サーバー側自作実装。PostgreSQL wire の
`SSLRequest`・NoSQL 表層の HTTPS いずれも外部 TLS クレートへ依存しない
方針）は鍵交換グループとして X25519 のみを採用する。本 Issue はその
構成要素として、曲線 25519 上の Diffie-Hellman 関数 X25519 を定数時間で
実装する（`crates/wire-server/src/tls/field25519.rs`・`x25519.rs`）。

key_share 拡張の解析（#954）・HKDF／鍵スケジュール（#956）・alert 型や
ハンドシェイク状態機械（#965）・接続への結線（#966 以降）・Ed25519 固有の
演算（平方根・点圧縮等。#961）はいずれも対象外。

## 表現・定数時間性の根拠

- `Fe([u64; 5])`: 基数 2^51・5 limb のリトルエンディアン表現（curve25519
  系実装で広く用いられる公知の手法）。乗算は `u128` へ 5×5 の limb 積を
  蓄積し、2^255 ≡ 19（mod p）で高位項を折り返してから 2 回の桁上げで
  各 limb を 2^51 未満へ畳み込む。
- 秘密値（ladder 中の座標・スカラー）に依存する分岐・配列添字・テーブル
  参照は持たない:
  - Montgomery ladder のループカウンタ `t`（255 回固定）は公開値であり、
    スカラーバイト添字 `k[t >> 3]` は `t` にのみ依存する。
  - ladder 内のスワップは `Fe::cswap`（`mask = 0 - choice` による XOR
    マスク）のみで行い、`if` を使わない。
  - フィールド逆元（`Fe::invert`）はフェルマーの小定理 `a^(p-2)` を
    固定長の加算連鎖（254 回の平方・11 回の乗算。curve25519 系実装で
    公知の手法）で計算し、値に依存するループ回数を持たない。
- 唯一の「値に依存する分岐」は共有秘密が全ゼロ（低次点入力）かどうかの
  判定（`is_all_zero`）であり、これはハンドシェイクを継続するか中断
  するかという外部から観測可能な公開の事実にのみ関わる（秘密スカラー
  自体の値はこの分岐の入力ではない）。

## 非正準入力・正準出力

- `Fe::from_bytes` は RFC 7748 §5 の decodeUCoordinate に従い最上位ビット
  （bit 255）を無条件でマスクし、`p` 以上の非正準値もそのまま受理する
  （演算過程で mod p として扱われる）。
- `Fe::to_bytes` は `(limb + 19) >> 51` の桁上げ連鎖による商 `q ∈ {0, 1}`
  の算出（分岐なしのマスク演算）で完全に正準化した表現を返す。

## API・TLS alert 写像

- `x25519(scalar, u) -> [u8; 32]`: RFC 7748 の生関数（クランプ込み・
  全ゼロ判定なし）。テストベクタ照合・下位プリミティブ用。
- `EphemeralSecret::generate` / `from_bytes` / `public_key` /
  `diffie_hellman`: TLS ハンドシェイクの実運用経路。`diffie_hellman` は
  `self` を消費し一時鍵の型レベルでの再利用防止、peer 公開鍵の長さを
  `try_from` で厳密検証（`unwrap`/`expect`/可変長スライス添字は不使用）、
  全ゼロ共有秘密を `Err(X25519Error::AllZeroSharedSecret)` として拒否
  する。
- `X25519Error::alert_description`: `InvalidPublicKeyLength` ／
  `AllZeroSharedSecret` いずれも TLS `handshake_failure`（alert code
  40。RFC 8446）へ写像する。alert の実送出経路は #965 の担当であり、
  本関数はその際の単一情報源として参照・置換される前提。

## 検証

RFC 7748 の公開テストベクタをそのまま用いて固定した（記憶からの
再構成ではなく、公開仕様書のテキストから正確に転記して機械検証済み）:

- §5.2 単発ベクタ 2 件
- §5.2 反復テスト（1 回・1,000 回。1,000,000 回は `#[ignore]` の追加
  検証としてのみ実行し、受入基準には使わない）
- §6.1 Alice/Bob 鍵交換例（双方の公開鍵・共有秘密が記載値と一致）
- 低次点拒否: u = 0、u = 1、u = p（非正準）、u = p + 1（非正準）
- 長さ不正拒否: 0・31・33・64 バイト
- クランプの冪等性・ビットパターン
- クランプで無視されるビットに対する `x25519` の結果不変性
- `Debug` 出力に鍵バイトが含まれないこと
- `generate()` による鍵ペア同士の DH 一致

## 残余リスク・申し送り（#971 監査への申し送り）

- 秘密値のメモリ上ゼロ化（`write_volatile` 等）は依存追加・`unsafe`
  なしでは保証できないため本 Issue のスコープ外。`Debug` の秘匿・
  `Clone` 非導出・`diffie_hellman(self)` の所有権消費に留める。
- `u128` を用いた乗算がターゲット（x86_64・aarch64）で定数時間である
  ことを前提とする。`crates/engine` 向けの `make check-cross` は
  wire-server を対象に含まない。
- コンパイラ最適化によるマスク演算（`cswap` 等）の分岐化はレビューと
  必要なら生成コード確認で担保する（本 Issue の範囲では未実施）。
